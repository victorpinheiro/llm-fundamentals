P8 — Múltiplos Agentes (com evidência)

Módulo: Módulo 9 — Múltiplos Agentes e Protocolos · Tempo: 16–20h · Degrau 4

Pré-condição — a parte mais importante

Você só implementa se mediu que o agente único foi insuficiente.

Responda com números do P7:

  • Há subtarefas com capacidades fundamentalmente diferentes?
  • Paralelismo reduziria o tempo total de forma substancial? Quanto?
  • O contexto combinado estoura a janela? Com que tamanho?

Se nenhuma resposta tem número, volte ao P7.

Resultado válido: não implementar

Se a medição mostrar que o agente único atende, o entregável deste
projeto é o documento explicando isso, com os números.

Isso não é falhar no projeto. É o julgamento que a função exige.
Boa parte dos sistemas multi-agente em produção não deveria existir.

Se justificar

Entrada → Orquestrador → [Especialista A ‖ Especialista B] → Crítico → Saída

Regras:
- Cada especialista recebe apenas suas ferramentas
- Orquestrador só roteia
- Crítico usa critério categórico
- Orçamento de tokens por execução
- Sanitização entre agentes

Comparação obrigatória

Agente único (P7) Múltiplos (P8)
Latência p95
Custo por execução
Qualidade
Linhas de código
Tempo para depurar uma falha

A última linha é a mais reveladora e a mais esquecida.

Passo a passo

Passo 1 — Avaliar se múltiplos agentes se justificam

Antes de escrever qualquer código, preencha o documento de decisão com números reais do P7. Use este template como ponto de partida para docs/decisao.md:

# Documento de Decisão: Agente Único vs. Múltiplos Agentes

## Pergunta 1 — Há subtarefas com capacidades fundamentalmente diferentes?
[Liste as subtarefas do seu agente P7 e as ferramentas que cada uma usa.
Se todas usam o mesmo conjunto de ferramentas, a resposta é não.]

## Pergunta 2 — Paralelismo reduziria o tempo total de forma substancial?
[Meça a latência das subtarefas individualmente. Se são sequenciais por
natureza (saída de uma alimenta a próxima), paralelismo não ajuda.]

## Pergunta 3 — O contexto combinado estoura a janela?
[Some o tamanho médio dos contextos. Se cabe na janela com folga, não
há necessidade de separar agentes para economizar contexto.]

## Conclusão
[Agente único é suficiente / Múltiplos agentes se justificam porque ___]

Exemplo de conclusão "não implementar":

Meu agente P7 executa todas as tarefas em média 3.2s a $0.004/chamada.
As subtarefas (busca, análise, resposta) usam as mesmas ferramentas.
Paralelismo economizaria ~1s mas adicionaria complexidade de orquestração.
Contexto em 2k tokens, bem dentro da janela de 128k.
Conclusão: agente único é suficiente. O ganho não justifica a complexidade.

Isso é o entregável. Não precisa ir ao Passo 2.

Passo 2 — Projetar o orquestrador (se justificado)

Se a análise mostrou justificativa, projete a arquitetura usando o padrão Orquestrador-Especialista-Crítico:

┌─────────────────────────────────────────────────────────┐
│                    ORQUESTRADOR                         │
│  - Recebe a requisição do usuário                       │
│  - Decide qual(is) especialista(s) acionar              │
│  - Agrega os resultados                                 │
│  - Controla orçamento de tokens                         │
└──────────┬──────────────────────┬───────────────────────┘
           │                      │
     ┌─────▼─────┐         ┌─────▼─────┐
     │ ESPEC. A  │         │ ESPEC. B  │
     │           │         │           │
     │ tools: [  │         │ tools: [  │
     │  busca,   │         │  cálculo, │
     │  leitura  │         │  gráfico  │
     │ ]         │         │ ]         │
     └─────┬─────┘         └─────┬─────┘
           │                      │
           └──────────┬───────────┘
                ┌─────▼─────┐
                │  CRÍTICO  │
                │           │
                │ Avalia o  │
                │ resultado │
                │ combinado │
                │ com pass/ │
                │ fail      │
                └───────────┘

Cada componente tem uma responsabilidade clara:

  • Orquestrador: recebe a requisição, decide quais especialistas chamar, agrega resultados. Não executa tarefas diretamente.
  • Especialistas: cada um tem seu próprio system prompt e acesso apenas às suas ferramentas. Vê apenas o contexto necessário para sua tarefa.
  • Crítico: avalia o resultado combinado com critérios categóricos (pass/fail), não subjetivos. Exemplo: "A resposta cita pelo menos uma fonte?" em vez de "A resposta é boa?".

Passo 3 — Implementar com código

Trilha A — OpenAI Agents SDK

from agents import Agent, Runner
import asyncio

# --- Especialistas (cada um com ferramentas isoladas) ---
especialista_busca = Agent(
    name="Buscador",
    instructions="Você busca informações relevantes. Retorne apenas fatos.",
    tools=[ferramenta_busca],  # Só recebe as ferramentas que precisa
)

especialista_analise = Agent(
    name="Analista",
    instructions="Você analisa dados e produz conclusões estruturadas.",
    tools=[ferramenta_calculo],
)

# --- Crítico ---
critico = Agent(
    name="Critico",
    instructions="""Avalie o resultado combinado com estes critérios:
1. FONTES: A resposta cita pelo menos uma fonte verificável? (pass/fail)
2. COERÊNCIA: A conclusão segue logicamente dos dados? (pass/fail)
3. COMPLETUDE: Todas as partes da pergunta foram respondidas? (pass/fail)

Responda APENAS com: APROVADO (todos pass) ou REPROVADO (qualquer fail).
Se REPROVADO, diga qual critério falhou e por quê.""",
)

# --- Orquestrador ---
orquestrador = Agent(
    name="Orquestrador",
    instructions="Coordene os especialistas para responder à pergunta do usuário.",
    handoffs=[especialista_busca, especialista_analise, critico],
)

async def executar(pergunta: str):
    resultado = await Runner.run(orquestrador, input=pergunta)
    return resultado.final_output

Track C — Multi-agent with free providers

For Track C, the multi-agent pattern works the same way. Use LangGraph as the orchestration framework with any free provider as the LLM backend.

"""p8_multi/orchestrator_free.py — Multi-agent with free providers"""
import os
from langgraph.prebuilt import create_react_agent
from langchain_openai import ChatOpenAI
from langchain_core.tools import tool

# -- Pick your free provider -------------------------------------------
# Option 1: Groq (fast, cloud-based, free)
model = ChatOpenAI(
    model="llama-3.3-70b-versatile",
    api_key=os.getenv("GROQ_API_KEY"),
    base_url="https://api.groq.com/openai/v1",
)

# Option 2: Ollama (local, free, no API key needed)
# model = ChatOpenAI(
#     model="llama3.2",
#     base_url="http://localhost:11434/v1",
#     api_key="ollama",
# )

# Option 3: Gemini via langchain-google-genai
# from langchain_google_genai import ChatGoogleGenerativeAI
# model = ChatGoogleGenerativeAI(model="gemini-2.0-flash")

# -- Specialists (each with isolated tools) ----------------------------
@tool
def search_documents(query: str) -> str:
    """Search the knowledge base for relevant documents."""
    from p5_rag.retriever import search
    import json
    return json.dumps([{"text": r["text"][:500], "source": r.get("url", "")} for r in search(query)])

@tool
def analyze_data(data: str) -> str:
    """Analyze data and return structured conclusions."""
    import json
    return json.dumps({"analysis": f"Analysis of: {data[:200]}"})

specialist_search = create_react_agent(model, [search_documents])
specialist_analysis = create_react_agent(model, [analyze_data])

# -- Orchestration with sequential calls -------------------------------
def run_multi_agent(question: str) -> str:
    """Run specialists sequentially and combine results."""
    # Step 1: Search specialist gathers information
    search_result = specialist_search.invoke(
        {"messages": [("user", f"Find relevant information about: {question}")]}
    )
    search_output = search_result["messages"][-1].content

    # Step 2: Analysis specialist processes the findings
    analysis_result = specialist_analysis.invoke(
        {"messages": [("user", f"Analyze these findings:\n{search_output}\n\nOriginal question: {question}")]}
    )
    analysis_output = analysis_result["messages"][-1].content

    # Step 3: Critic evaluates (can use a simpler/cheaper model)
    critic_response = model.invoke(
        f"""Evaluate this result with these criteria:
1. SOURCES: Does the answer cite at least one verifiable source? (pass/fail)
2. COHERENCE: Does the conclusion follow logically from the data? (pass/fail)
3. COMPLETENESS: Were all parts of the question answered? (pass/fail)

Result to evaluate:
{analysis_output}

Reply ONLY with: APPROVED (all pass) or REJECTED (any fail).
If REJECTED, state which criterion failed and why."""
    )

    return f"Answer: {analysis_output}\n\nCritic: {critic_response.content}"

Cost note: With free providers, cost per execution is $0.00. The comparison table between P7 and P8 should show $0.00 for both — the decision to use multi-agent is driven entirely by latency, quality, and complexity trade-offs, not cost.

Passo 4 — Implementar sanitização entre agentes

Sanitização significa validar e limpar os dados que um agente passa para outro, para evitar que saída malformada ou injetada de um especialista comprometa o próximo.

import re
from pydantic import BaseModel, field_validator

class ResultadoEspecialista(BaseModel):
    """Valida a saída de um especialista antes de passar ao próximo."""
    conteudo: str
    fontes: list[str]
    confianca: float

    @field_validator("conteudo")
    @classmethod
    def limpar_conteudo(cls, v: str) -> str:
        # Remove possíveis instruções injetadas
        v = re.sub(r"(?i)(ignore previous|system prompt|you are now)", "[REMOVIDO]", v)
        # Limita tamanho para não estourar contexto do próximo agente
        if len(v) > 5000:
            v = v[:5000] + "\n[TRUNCADO]"
        return v

    @field_validator("confianca")
    @classmethod
    def validar_confianca(cls, v: float) -> float:
        if not 0.0 <= v <= 1.0:
            raise ValueError(f"Confiança deve estar entre 0 e 1, recebeu {v}")
        return v

def sanitizar_entre_agentes(saida_bruta: str) -> ResultadoEspecialista:
    """Valida saída antes de passá-la ao próximo agente."""
    try:
        resultado = ResultadoEspecialista.model_validate_json(saida_bruta)
        return resultado
    except Exception as e:
        raise ValueError(f"Saída do especialista não passou na validação: {e}")

Passo 5 — Preencher a tabela de comparação P7 vs P8

Para medir corretamente cada métrica:

import time
import numpy as np

# --- Coletar latências em N execuções ---
latencias_p7 = []
latencias_p8 = []
custos_p7 = []
custos_p8 = []

casos_teste = carregar_casos_teste()  # Seus 40+ casos do P3

for caso in casos_teste:
    # Medir P7 (agente único)
    inicio = time.perf_counter()
    resultado_p7 = executar_agente_p7(caso["input"])
    latencias_p7.append(time.perf_counter() - inicio)
    custos_p7.append(calcular_custo(resultado_p7))

    # Medir P8 (múltiplos agentes)
    inicio = time.perf_counter()
    resultado_p8 = executar_agente_p8(caso["input"])
    latencias_p8.append(time.perf_counter() - inicio)
    custos_p8.append(calcular_custo(resultado_p8))

# --- Calcular p95 ---
p95_p7 = np.percentile(latencias_p7, 95)
p95_p8 = np.percentile(latencias_p8, 95)

print(f"Latência p95 — P7: {p95_p7:.2f}s | P8: {p95_p8:.2f}s")
print(f"Custo médio  — P7: ${np.mean(custos_p7):.4f} | P8: ${np.mean(custos_p8):.4f}")

O p95 (percentil 95) significa: 95% das execuções terminaram em menos que esse tempo. Ordene as latências, pegue o valor na posição 0.95 * len(latencias). Isso captura os casos lentos sem ser distorcido por outliers extremos como o máximo seria.

Passo 6 — Escrever a conclusão honesta

A conclusão deve responder: "Valeu a pena?" com números. Template:

# Conclusão

## O que mudou de P7 para P8
- Latência p95: X.Xs → Y.Ys (melhoria/piora de Z%)
- Custo por execução: $X → $Y (melhoria/piora de Z%)
- Qualidade (score médio de avaliação): X → Y

## O que ficou mais complexo
- Linhas de código: N → M
- Tempo para depurar uma falha: descreva um caso real
- Componentes para manter: 1 → K

## Veredicto
[Multi-agente se justificou / não se justificou] porque [razão com números].
Se fosse começar de novo, [manteria a decisão / faria diferente porque ___].

Quando múltiplos agentes valem a pena

Use este framework para a decisão. A barra é alta de propósito.

Cenário Vale a pena? Por quê
Subtarefas usam modelos diferentes (ex: um barato para triagem, um caro para análise) Provavelmente sim Economia real de custo mensurável
Subtarefas podem rodar em paralelo e latência importa Provavelmente sim Ganho de tempo multiplicativo, não marginal
Contexto combinado estoura a janela do modelo Sim Sem alternativa: precisa separar para funcionar
Subtarefas precisam de ferramentas com riscos diferentes (ex: leitura vs. escrita) Provavelmente sim Isolamento de ferramentas reduz superfície de ataque
"Quero que cada agente tenha personalidade" Não System prompt resolve. Não precisa de agentes separados
"Parece mais organizado" Não Organização vem de código limpo, não de agentes
Tudo cabe em um contexto e roda em tempo aceitável Não Complexidade adicionada sem ganho mensurável

Regra prática: se você não consegue apontar um número que melhora (latência, custo, qualidade), não implemente múltiplos agentes.
