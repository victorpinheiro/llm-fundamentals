P9 — Projeto Final: Engajamento Completo

Módulo: Módulo 11 — Entrega de Sistemas de IA · Tempo: 40–60h

Objetivo

Percorrer um engajamento completo: descoberta, desenho, implementação,
avaliação, entrega.

Este é o projeto que demonstra competência de forma verificável.

Escolha um cenário

A — Assistente sobre base documental
Uma equipe jurídica gasta em média 45 minutos por consulta procurando cláusulas em contratos espalhados por SharePoint, e-mail e pastas locais. Erros de interpretação já causaram retrabalho significativo. O assistente deve responder perguntas sobre a base documental citando o documento e trecho exatos.

  • Fontes de dados sugeridas: PDFs de contratos, termos de serviço, manuais internos (use documentos públicos se não tiver acesso a reais)
  • Complexidade esperada: Degraus 1-3 da Escada (prompt estruturado + RAG). Múltiplos agentes provavelmente não se justificam
  • Projetos anteriores a reaproveitar: P1 (saída estruturada), P2 (iteração de prompt), P5 (RAG), P3 (avaliação)

B — Processamento de documentos
Uma empresa recebe 200+ notas fiscais por mês em PDF. Hoje, um estagiário digita manualmente CNPJ, valores e itens numa planilha — processo que leva 3 dias e tem taxa de erro de ~5%. O sistema deve extrair campos estruturados automaticamente e sinalizar documentos que precisam de revisão humana.

  • Fontes de dados sugeridas: PDFs de notas fiscais (gere exemplos sintéticos com dados fictícios se necessário)
  • Complexidade esperada: Degraus 1-2 (prompt com saída estruturada + validação). Pode subir para Degrau 3 se precisar de RAG para consultar regras fiscais
  • Projetos anteriores a reaproveitar: P1 (saída estruturada com Pydantic), P2 (iteração), P3 (avaliação), P4 (roteamento por tipo de documento)

C — Triagem e roteamento
Uma equipe de suporte recebe 500+ tickets por semana via formulário. Hoje, um coordenador lê cada um, classifica por área (billing, técnico, produto, urgente) e atribui manualmente. O tempo médio de triagem é 8 minutos por ticket, e 15% são classificados errado. O sistema deve classificar, priorizar e rotear automaticamente, com escalação para humano quando a confiança for baixa.

  • Fontes de dados sugeridas: Dataset de tickets de suporte (use dados públicos como o dataset de customer support do Kaggle ou gere sintéticos)
  • Complexidade esperada: Degraus 1-3 (classificação + roteamento). Pode justificar Degrau 4 (múltiplos agentes) se triagem e resposta forem paralelas
  • Projetos anteriores a reaproveitar: P1 (classificação estruturada), P4 (roteamento de modelos), P6 (integração corporativa), P7 (agente)

Se puder fazer com uma pessoa real que tenha o problema, faça.
Um engajamento real vale muito mais que um simulado.

Fase 1 — Descoberta

Conduza as seis perguntas com alguém que tenha o problema.
Se não tiver acesso a essa pessoa, escreva a partir de um caso realista
e seja explícito sobre a simulação.

As seis perguntas de descoberta:

  1. Qual é o problema concreto? — O que acontece hoje, com que frequência, e quanto custa (tempo, dinheiro, erros)?
  2. Quem sofre com o problema? — Qual a pessoa, papel, e como o dia dela é afetado?
  3. Como resolvem hoje? — Qual o processo atual, passo a passo? Onde falha?
  4. O que "resolvido" parece? — Qual a métrica de sucesso? Como saberemos que funcionou?
  5. Que dados existem? — Que documentos, bases, APIs estão disponíveis? Em que formato?
  6. Quais as restrições? — Privacidade, compliance, latência, custo máximo, integrações obrigatórias?

Template para 01_descoberta/descoberta.md:

# Descoberta — [Nome do Projeto]

## 1. Problema
[Descrição concreta. Ex: "A equipe jurídica gasta em média 45 minutos
por consulta procurando cláusulas em contratos distribuídos em 3 sistemas.
São ~20 consultas/semana. Isso consome 15h/semana de trabalho de advogados
a R$200/h = R$3.000/semana."]

## 2. Quem sofre
[Ex: "3 advogados juniores que fazem due diligence. Frustração alta,
turnover de 40% no último ano parcialmente atribuído a trabalho repetitivo."]

## 3. Processo atual
1. Recebe pedido por e-mail
2. Abre SharePoint e busca por palavra-chave
3. Abre cada documento e lê manualmente
4. Copia trecho relevante para o parecer
5. Tempo médio: 45 min. Taxa de erro: ~10% (trecho errado ou desatualizado)

## 4. Definição de sucesso
- Tempo de consulta reduzido para <5 minutos
- Taxa de erro <2%
- Advogados confiam o suficiente para usar sem verificar cada resposta

## 5. Dados disponíveis
- 500 contratos em PDF no SharePoint (acesso via API Microsoft Graph)
- Modelos de parecer em Word
- Histórico de consultas em e-mail (não estruturado)

## 6. Restrições
- Dados confidenciais: não podem sair do ambiente corporativo
- Latência aceitável: até 30 segundos por consulta
- Orçamento: até R$500/mês em API
- Precisa funcionar com SSO da empresa

## Nota sobre simulação
[Se simulado: "Este cenário é baseado em entrevistas com X, adaptado
para fins educacionais. Os dados reais foram substituídos por sintéticos."]

Fase 2 — Desenho

Aplique a A Escada de Complexidade. Para cada degrau que subir, escreva por
quê, com o que sustentaria a decisão.

Template para 02_desenho/decisoes.md:

# Decisões de Arquitetura — [Nome do Projeto]

| Nível | Descrição                    | Tentei? | Resultado                                    | Por que subir?                                         |
|-------|------------------------------|---------|----------------------------------------------|--------------------------------------------------------|
| 1     | Prompt único                 | Sim     | Acurácia 62% nos 40 casos de teste           | Abaixo do mínimo aceitável (80%)                       |
| 2     | Prompt otimizado + few-shot  | Sim     | Acurácia 78%, mas alucina em docs longos     | Perto do alvo, mas alucinação é inaceitável para legal |
| 3     | RAG com base vetorial        | Sim     | Acurácia 91%, latência 4s, custo $0.003/call | Atende os critérios. Parei aqui                        |
| 4     | Múltiplos agentes            | Não     | —                                            | Não necessário: métricas do nível 3 atendem            |

## Decisão final
Implementação no Nível 3 (RAG). Justificativa:
- Acurácia 91% > meta de 80%
- Latência 4s < limite de 30s
- Custo $0.003/call × 100 calls/dia = $9/mês < orçamento de R$500/mês

Para cada nível, mostre o teste real que fez — não escreva "não tentei" sem ter testado pelo menos um prompt básico no nível 1.

  • Faça commits frequentes com mensagens que incluam as métricas: "nível 2: acurácia 62% → 78%"

Fase 4 — Avaliação e observabilidade

  • Conjunto de referência de 40 ou mais casos
  • Avaliação em CI
  • Rastreamento configurado
  • Quatro alertas, cada um disparado uma vez para teste
  • Revisão de segurança completa

Template para 04_avaliacao/avaliacao.md:

# Avaliação — [Nome do Projeto]

## Dataset de referência
- Total de casos: [N, mínimo 40]
- Distribuição: [ex: 15 consultas simples, 15 complexas, 10 edge cases]
- Fonte: [como foram criados — reais, sintéticos, mix]

## Métricas
| Métrica              | Baseline (Nível 1) | Atual (Nível N) | Meta      |
|----------------------|---------------------|------------------|-----------|
| Acurácia             |                     |                  |           |
| Latência p95         |                     |                  |           |
| Custo por execução   |                     |                  |           |
| Taxa de alucinação   |                     |                  |           |

## Alertas configurados
| #  | Alerta                              | Condição                  | Testado? |
|----|--------------------------------------|---------------------------|----------|
| 1  | Latência alta                        | p95 > 5 segundos           | [ ]      |
| 2  | Taxa de erro                         | > 5% em janela de 1 hora  | [ ]      |
| 3  | Custo diário                         | > $X/dia                   | [ ]      |
| 4  | Queda de qualidade                   | Score eval < baseline      | [ ]      |

Exemplo de alerta básico com Python:

import logging
import httpx  # ou requests

logger = logging.getLogger("alertas")

def verificar_e_alertar(metricas: dict, webhook_url: str | None = None):
    """Verifica métricas e dispara alertas se necessário."""
    alertas = []

    if metricas["latencia_p95"] > 5.0:
        alertas.append(f"ALERTA: Latência p95 em {metricas['latencia_p95']:.1f}s (limite: 5s)")

    if metricas["taxa_erro"] > 0.05:
        alertas.append(f"ALERTA: Taxa de erro em {metricas['taxa_erro']:.1%} (limite: 5%)")

    if metricas["custo_diario"] > metricas["custo_limite"]:
        alertas.append(f"ALERTA: Custo diário ${metricas['custo_diario']:.2f} (limite: ${metricas['custo_limite']:.2f})")

    if metricas["eval_score"] < metricas["eval_baseline"]:
        alertas.append(f"ALERTA: Score {metricas['eval_score']:.2f} abaixo do baseline {metricas['eval_baseline']:.2f}")

    for alerta in alertas:
        logger.warning(alerta)
        if webhook_url:
            httpx.post(webhook_url, json={"text": alerta})

    return alertas

Cada alerta deve ser disparado uma vez intencionalmente (ex: passe um timeout baixo para forçar o alerta de latência) para provar que funciona.

Fase 5 — Entrega

  • Demonstração de dez minutos gravada

Template para 05_entrega/operacao.md:

# Manual de Operação — [Nome do Projeto]

## Alerta 1 — Latência alta (p95 > 5s)
**Possíveis causas:** API do provedor lenta, documentos muito grandes no retriever, modelo sobrecarregado
**O que fazer:**
1. Verificar status page do provedor (status.openai.com / status.cloud.google.com)
2. Checar logs para identificar quais requests estão lentas
3. Se for tamanho de documento: revisar chunking no retriever
4. Se for sistêmico: considerar fallback para modelo mais rápido (ver P4)

## Alerta 2 — Taxa de erro > 5%
**Possíveis causas:** input malformado, mudança na API, limite de rate atingido
**O que fazer:**
1. Checar logs de erro para padrão (mesmo tipo de input? mesmo endpoint?)
2. Verificar se houve mudança na API do provedor
3. Se rate limit: implementar backoff exponencial ou reduzir concorrência

## Alerta 3 — Custo diário acima do limite
**Possíveis causas:** aumento de uso, prompts maiores que esperado, loop infinito
**O que fazer:**
1. Verificar volume de requests (aumento legítimo vs. anomalia)
2. Checar tamanho médio de prompt (mudou?)
3. Procurar loops: agente chamando ferramenta repetidamente sem progresso

## Alerta 4 — Score de avaliação abaixo do baseline
**Possíveis causas:** mudança no modelo, dados de entrada diferentes, drift
**O que fazer:**
1. Rodar avaliação completa manualmente para confirmar
2. Comparar resultados caso a caso com o baseline
3. Se confirmado: investigar se mudou o modelo, os dados, ou o prompt

Como gravar a demo

A demonstração gravada de 10 minutos é parte do entregável. Estrutura sugerida:

Tempo Conteúdo Dica
0:00–1:30 Problema — Qual o problema, quem sofre, quanto custa Comece pelo impacto, não pela tecnologia
1:30–3:00 Solução — Arquitetura escolhida e por quê (mostre a Escada) Explique o que descartou e por quê
3:00–6:00 Demo ao vivo — Mostre o sistema funcionando com casos reais Inclua pelo menos um caso difícil ou edge case
6:00–7:30 Limitações — O que não funciona, onde falha, o que falta Honestidade aqui demonstra maturidade
7:30–9:00 Métricas — Acurácia, latência, custo, comparação entre níveis Mostre a tabela de decisões preenchida
9:00–10:00 Lições — O que aprendeu, o que faria diferente Uma ou duas lições genuínas valem mais que lista longa

Ferramentas sugeridas para gravação:

  • OBS Studio — gratuito, código aberto, funciona em Windows/Mac/Linux. Configure para capturar tela + áudio do microfone. Resolução 1920x1080, 30fps é suficiente
  • Loom — mais simples, grava direto do navegador, versão gratuita com limite de 5 minutos por vídeo (grave em duas partes se necessário)

Dica: ensaie uma vez antes de gravar. A primeira tentativa sempre leva 15+ minutos.

Links de referência

  • OBS Studio — gravação de tela gratuita e código aberto
  • Loom — gravação de tela simplificada
  • Pydantic — validação de schemas de entrada e saída
  • pytest — framework de testes para avaliação automatizada
