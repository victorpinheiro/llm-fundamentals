P9 — Projeto Final: Engajamento Completo

Módulo: Módulo 11 — Entrega de Sistemas de IA · Tempo: 40–60h

Objetivo

Percorrer um engajamento completo: descoberta, desenho, implementação,
avaliação, entrega.

Este é o projeto que demonstra competência de forma verificável.

Escolha um cenário

A — Assistente sobre base documental
Uma equipe jurídica gasta em média 45 minutos por consulta procurando cláusulas em contratos espalhados por SharePoint, e-mail e pastas locais. Erros de interpretação já causaram retrabalho significativo. O assistente deve responder perguntas sobre a base documental citando o documento e trecho exatos.

  • Fontes de dados sugeridas: PDFs de contratos, termos de serviço, manuais internos (use documentos públicos se não tiver acesso a reais)
  • Complexidade esperada: Degraus 1-3 da Escada (prompt estruturado + RAG). Múltiplos agentes provavelmente não se justificam
  • Projetos anteriores a reaproveitar: P1 (saída estruturada), P2 (iteração de prompt), P5 (RAG), P3 (avaliação)

B — Processamento de documentos
Uma empresa recebe 200+ notas fiscais por mês em PDF. Hoje, um estagiário digita manualmente CNPJ, valores e itens numa planilha — processo que leva 3 dias e tem taxa de erro de ~5%. O sistema deve extrair campos estruturados automaticamente e sinalizar documentos que precisam de revisão humana.

  • Fontes de dados sugeridas: PDFs de notas fiscais (gere exemplos sintéticos com dados fictícios se necessário)
  • Complexidade esperada: Degraus 1-2 (prompt com saída estruturada + validação). Pode subir para Degrau 3 se precisar de RAG para consultar regras fiscais
  • Projetos anteriores a reaproveitar: P1 (saída estruturada com Pydantic), P2 (iteração), P3 (avaliação), P4 (roteamento por tipo de documento)

C — Triagem e roteamento
Uma equipe de suporte recebe 500+ tickets por semana via formulário. Hoje, um coordenador lê cada um, classifica por área (billing, técnico, produto, urgente) e atribui manualmente. O tempo médio de triagem é 8 minutos por ticket, e 15% são classificados errado. O sistema deve classificar, priorizar e rotear automaticamente, com escalação para humano quando a confiança for baixa.

  • Fontes de dados sugeridas: Dataset de tickets de suporte (use dados públicos como o dataset de customer support do Kaggle ou gere sintéticos)
  • Complexidade esperada: Degraus 1-3 (classificação + roteamento). Pode justificar Degrau 4 (múltiplos agentes) se triagem e resposta forem paralelas
  • Projetos anteriores a reaproveitar: P1 (classificação estruturada), P4 (roteamento de modelos), P6 (integração corporativa), P7 (agente)

Se puder fazer com uma pessoa real que tenha o problema, faça.
Um engajamento real vale muito mais que um simulado.

Fase 1 — Descoberta

Conduza as seis perguntas com alguém que tenha o problema.
Se não tiver acesso a essa pessoa, escreva a partir de um caso realista
e seja explícito sobre a simulação.

As seis perguntas de descoberta:

  1. Qual é o problema concreto? — O que acontece hoje, com que frequência, e quanto custa (tempo, dinheiro, erros)?
  2. Quem sofre com o problema? — Qual a pessoa, papel, e como o dia dela é afetado?
  3. Como resolvem hoje? — Qual o processo atual, passo a passo? Onde falha?
  4. O que "resolvido" parece? — Qual a métrica de sucesso? Como saberemos que funcionou?
  5. Que dados existem? — Que documentos, bases, APIs estão disponíveis? Em que formato?
  6. Quais as restrições? — Privacidade, compliance, latência, custo máximo, integrações obrigatórias?

Template para 01_descoberta/descoberta.md:

# Discovery — [Project Name]

## 1. Problem
[Concrete description. E.g.: "The legal team spends an average of 45 minutes
per query searching for clauses in contracts spread across 3 systems.
That's ~20 queries/week. This consumes 15h/week of lawyer time
at R$200/h = R$3,000/week."]

## 2. Who is affected
[E.g.: "3 junior lawyers doing due diligence. High frustration,
40% turnover last year partially attributed to repetitive work."]

## 3. Current process
1. Receives request via email
2. Opens SharePoint and searches by keyword
3. Opens each document and reads manually
4. Copies relevant excerpt to the legal opinion
5. Average time: 45 min. Error rate: ~10% (wrong or outdated excerpt)

## 4. Definition of success
- Query time reduced to <5 minutes
- Error rate <2%
- Lawyers trust it enough to use without verifying every answer

## 5. Available data
- 500 contracts in PDF on SharePoint (access via Microsoft Graph API)
- Legal opinion templates in Word
- Query history in email (unstructured)

## 6. Constraints
- Confidential data: cannot leave the corporate environment
- Acceptable latency: up to 30 seconds per query
- Budget: up to R$500/month on API
- Must work with the company's SSO

## Note on simulation
[If simulated: "This scenario is based on interviews with X, adapted
for educational purposes. Real data was replaced with synthetic data."]

Template para 02_desenho/decisoes.md:

# Architecture Decisions — [Project Name]

| Level | Description                  | Tried?  | Result                                       | Why escalate?                                          |
|-------|------------------------------|---------|----------------------------------------------|--------------------------------------------------------|
| 1     | Single prompt                | Yes     | 62% accuracy on 40 test cases                | Below minimum acceptable (80%)                         |
| 2     | Optimized prompt + few-shot  | Yes     | 78% accuracy, but hallucinates on long docs  | Close to target, but hallucination unacceptable for legal |
| 3     | RAG with vector store        | Yes     | 91% accuracy, 4s latency, $0.003/call cost   | Meets criteria. Stopped here                           |
| 4     | Multiple agents              | No      | —                                            | Not needed: level 3 metrics are sufficient             |

## Final decision
Implementation at Level 3 (RAG). Justification:
- 91% accuracy > 80% target
- 4s latency < 30s limit
- Cost $0.003/call x 100 calls/day = $9/month < R$500/month budget

Para cada nível, mostre o teste real que fez — não escreva "não tentei" sem ter testado pelo menos um prompt básico no nível 1.

Track C — Provider setup for the capstone

Track C students should use free providers throughout the capstone. Here is the provider setup code to use in src/config.py:

"""src/config.py — Provider configuration for Track C (free providers)"""
import os
from openai import OpenAI

# -- Choose your primary provider ------------------------------------
# All three are free. Pick based on your needs:
#   Gemini: best free embedding support, good for RAG-heavy projects
#   Groq:   fastest inference, great for latency-sensitive scenarios
#   Ollama: fully local, no API key needed, works offline

PROVIDER = os.getenv("LLM_PROVIDER", "groq")  # "gemini", "groq", or "ollama"

def get_client():
    """Return the configured LLM client."""
    if PROVIDER == "gemini":
        from google import genai
        return genai.Client(api_key=os.getenv("GEMINI_API_KEY"))

    elif PROVIDER == "groq":
        return OpenAI(
            api_key=os.getenv("GROQ_API_KEY"),
            base_url="https://api.groq.com/openai/v1",
        )

    elif PROVIDER == "ollama":
        return OpenAI(
            base_url="http://localhost:11434/v1",
            api_key="ollama",
        )

    raise ValueError(f"Unknown provider: {PROVIDER}")

def get_model_name() -> str:
    """Return the model name for the configured provider."""
    models = {
        "gemini": "gemini-2.0-flash",
        "groq": "llama-3.3-70b-versatile",
        "ollama": "llama3.2",
    }
    return models[PROVIDER]

def get_cost_per_call() -> float:
    """Return cost per API call. All Track C providers are free."""
    return 0.0

Capstone recommendations by scenario:

  • Scenario A (document assistant): Use Gemini for both embeddings (text-embedding-004) and generation (gemini-2.0-flash) -- simplest setup, single provider, free embeddings
  • Scenario B (document processing): Groq for fast structured extraction, or Ollama if the documents contain sensitive data that cannot leave the local machine
  • Scenario C (triage and routing): Groq for speed (500+ tickets/week demands low latency), with Ollama as a local fallback if Groq rate limits are hit

Cost note: With Track C providers, the "cost per execution" column in your evaluation table will be $0.00. Focus your comparison on latency, quality, and reliability instead. For the alert on daily cost, replace it with a rate-limit alert (e.g., "requests per minute exceeds provider free-tier limit").

# Evaluation — [Project Name]

## Reference dataset
- Total cases: [N, minimum 40]
- Distribution: [e.g.: 15 simple queries, 15 complex, 10 edge cases]
- Source: [how they were created — real, synthetic, mix]

## Metrics
| Metric               | Baseline (Level 1) | Current (Level N) | Target    |
|----------------------|---------------------|-------------------|-----------|
| Accuracy             |                     |                   |           |
| Latency p95          |                     |                   |           |
| Cost per execution   |                     |                   |           |
| Hallucination rate   |                     |                   |           |

## Configured alerts
| #  | Alert                               | Condition                 | Tested?  |
|----|--------------------------------------|---------------------------|----------|
| 1  | High latency                         | p95 > 5 seconds            | [ ]      |
| 2  | Error rate                           | > 5% in 1-hour window     | [ ]      |
| 3  | Daily cost                           | > $X/day                   | [ ]      |
| 4  | Quality drop                         | Eval score < baseline      | [ ]      |

Exemplo de alerta básico com Python:

import logging
import httpx  # or requests

logger = logging.getLogger("alerts")

def check_and_alert(metrics: dict, webhook_url: str | None = None):
    """Check metrics and fire alerts if needed."""
    alerts = []

    if metrics["latency_p95"] > 5.0:
        alerts.append(f"ALERT: Latency p95 at {metrics['latency_p95']:.1f}s (limit: 5s)")

    if metrics["error_rate"] > 0.05:
        alerts.append(f"ALERT: Error rate at {metrics['error_rate']:.1%} (limit: 5%)")

    if metrics["daily_cost"] > metrics["cost_limit"]:
        alerts.append(f"ALERT: Daily cost ${metrics['daily_cost']:.2f} (limit: ${metrics['cost_limit']:.2f})")

    if metrics["eval_score"] < metrics["eval_baseline"]:
        alerts.append(f"ALERT: Score {metrics['eval_score']:.2f} below baseline {metrics['eval_baseline']:.2f}")

    for alert in alerts:
        logger.warning(alert)
        if webhook_url:
            httpx.post(webhook_url, json={"text": alert})

    return alerts

Cada alerta deve ser disparado uma vez intencionalmente (ex: passe um timeout baixo para forçar o alerta de latência) para provar que funciona.

Template para 05_entrega/operacao.md:

# Operations Runbook — [Project Name]

## Alert 1 — High latency (p95 > 5s)
**Possible causes:** Slow provider API, oversized documents in the retriever, overloaded model
**What to do:**
1. Check the provider's status page (status.openai.com / status.cloud.google.com)
2. Review logs to identify which requests are slow
3. If document size: review chunking in the retriever
4. If systemic: consider fallback to a faster model (see P4)

## Alert 2 — Error rate > 5%
**Possible causes:** Malformed input, API change, rate limit reached
**What to do:**
1. Check error logs for a pattern (same input type? same endpoint?)
2. Verify whether the provider API changed
3. If rate limit: implement exponential backoff or reduce concurrency

## Alert 3 — Daily cost above limit
**Possible causes:** Usage increase, prompts larger than expected, infinite loop
**What to do:**
1. Check request volume (legitimate increase vs. anomaly)
2. Review average prompt size (did it change?)
3. Look for loops: agent calling a tool repeatedly without progress

## Alert 4 — Evaluation score below baseline
**Possible causes:** Model change, different input data, drift
**What to do:**
1. Run the full evaluation manually to confirm
2. Compare results case by case against the baseline
3. If confirmed: investigate whether the model, data, or prompt changed

Como gravar a demo

A demonstração gravada de 10 minutos é parte do entregável. Estrutura sugerida:

Tempo Conteúdo Dica
0:00–1:30 Problema — Qual o problema, quem sofre, quanto custa Comece pelo impacto, não pela tecnologia
1:30–3:00 Solução — Arquitetura escolhida e por quê (mostre a Escada) Explique o que descartou e por quê
3:00–6:00 Demo ao vivo — Mostre o sistema funcionando com casos reais Inclua pelo menos um caso difícil ou edge case
6:00–7:30 Limitações — O que não funciona, onde falha, o que falta Honestidade aqui demonstra maturidade
7:30–9:00 Métricas — Acurácia, latência, custo, comparação entre níveis Mostre a tabela de decisões preenchida
9:00–10:00 Lições — O que aprendeu, o que faria diferente Uma ou duas lições genuínas valem mais que lista longa

Ferramentas sugeridas para gravação:

  • OBS Studio — gratuito, código aberto, funciona em Windows/Mac/Linux. Configure para capturar tela + áudio do microfone. Resolução 1920x1080, 30fps é suficiente
  • Loom — mais simples, grava direto do navegador, versão gratuita com limite de 5 minutos por vídeo (grave em duas partes se necessário)

Dica: ensaie uma vez antes de gravar. A primeira tentativa sempre leva 15+ minutos.

Links de referência

  • OBS Studio — gravação de tela gratuita e código aberto
  • Loom — gravação de tela simplificada
  • Pydantic — validação de schemas de entrada e saída
  • pytest — framework de testes para avaliação automatizada
