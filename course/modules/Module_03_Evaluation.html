Módulo 3 — Avaliação e Testes

Projeto: P3 — Pipeline de Avaliação em CI · Conceito: Referência — Avaliação

Objetivo

Construir um pipeline de avaliação que roda em integração contínua e
falha quando a qualidade cai. Sair de "parece que funciona" para
"aqui estão os números".

Por que importa

Esta é a competência que mais diferencia um engenheiro de IA experiente
de um iniciante — e a mais frequentemente pulada.

Sem avaliação você não consegue: saber se uma mudança de prompt melhorou,
detectar regressão após atualização de modelo, ou dar a um stakeholder
qualquer garantia sobre o sistema.

Numa conversa com uma área de risco ou conformidade, é a avaliação que
permite aprovar o projeto. "Confie em mim" não é aprovável.

Conceitos

Por que testar IA é diferente

Software tradicional Sistema de IA
Saída determinística Varia entre execuções
assert x == y funciona Comparação exata é inútil
Correto é objetivo Frequentemente subjetivo
Quebra de forma ruidosa Degrada silenciosamente

Mesmo com temperatura zero, uma atualização do modelo pelo provedor pode
mudar as saídas sem aviso e sem que seu código tenha mudado.

Conjunto de referência

Casos de teste com respostas acordadas. É o alicerce de tudo.

Composição recomendada para um conjunto inicial de 40 casos:

Tipo Quantidade Propósito
Caminho feliz 15 Funcionamento básico
Ambíguo 15 Casos realmente difíceis
Borda 7 Entrada vazia, idioma inesperado, tamanho extremo
Adversarial 3 Tentativas de injeção de prompt

Versione o conjunto junto com o código. Ele evolui: toda vez que
descobrir um novo modo de falha, adicione um caso.

Modelo como avaliador

Usar um modelo forte para julgar a saída de outro. Resolve o problema de
avaliar qualidade semântica, que métricas de correspondência exata não
capturam.

Regra importante: use critérios categóricos, não escalas numéricas.

Bom:  "Aprovado ou Reprovado"
Bom:  "Bom / Neutro / Ruim"
Ruim: "Nota de 1 a 10"

Modelos produzem resultados inconsistentes em escalas contínuas —
pequenas mudanças na redação do prompt de avaliação deslocam as notas.
Julgamentos binários ou de três classes são bem mais reprodutíveis.

Níveis de teste

Nível Verifica Quando roda
Unidade Formato, restrições, uma chamada Toda mudança de prompt
Integração Pipeline completo Mudança de arquitetura
Regressão Casos que passavam continuam passando Todo release
Adversarial Injeção, jailbreak, borda Antes de produção

Métricas para sistemas de recuperação

Quando houver RAG (Módulo 6), meça separadamente:

  • Precisão de recuperação — os trechos recuperados são relevantes?
  • Cobertura de recuperação — todos os relevantes foram recuperados?
  • Fidelidade — a resposta se sustenta no contexto recuperado?
  • Relevância da resposta — responde à pergunta feita?

Separar isso importa: se a resposta está ruim, você precisa saber se o
problema é a recuperação ou a geração. São correções diferentes.

Geração sintética de casos

Algumas ferramentas geram pares de pergunta e resposta a partir do seu
próprio acervo de documentos. Isso resolve o problema mais comum na
prática: não existir conjunto anotado.

Casos sintéticos não substituem casos reais curados, mas dão um ponto
de partida quando não há nenhum.

Integração contínua

O objetivo final deste módulo é um pipeline que:

  1. Roda a avaliação a cada alteração
  2. Compara com a linha de base
  3. Falha se a qualidade cair abaixo do limite
  4. Reporta os números no pull request

Ferramentas de avaliação modernas integram com frameworks de teste
padrão, então isso é a mesma disciplina de CI que você já conhece.

Projeto

P3 — Pipeline de Avaliação em CI — conjunto de referência, avaliação
automatizada, portão de regressão em CI.

Autoavaliação

  1. Por que assert saida == esperado não funciona aqui?
  2. Por que critérios categóricos superam escalas de 1 a 10?
  3. A resposta do seu RAG está ruim. Como descobrir se o problema é
    recuperação ou geração?
  4. Que casos você inclui num conjunto de 40 e em que proporção?
  5. Seu sistema passou de 91% para 87% após mudar de modelo. O que fazer?

Erros comuns

  • Adiar avaliação para o final do projeto
  • Conjunto só com casos fáceis
  • Notas de 1 a 10
  • Não versionar o conjunto de referência
  • Avaliar recuperação e geração juntas, sem separar
