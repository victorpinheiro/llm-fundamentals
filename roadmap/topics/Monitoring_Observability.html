Monitoring & Observability

Fase: 3 | Semanas: 18–19

Perfil da função: "You build robust and resilient systems where maintenance is lower or
non-existent."

Sistema com pouca manutenção não é sistema sem monitoramento — é o contrário.
Você só pode ir embora se o sistema avisa quando quebra.

O que monitorar

Métrica Por quê
Token usage Previsão e controle de custo
Latência (p50/p95/p99) SLA e experiência
Error rate Saúde do sistema
Output drift Qualidade caiu sem o código mudar
Eval score contínuo Regressão silenciosa
Tool call success rate Saúde de agentes
Custo por run Cost explosion (failure mode do PDF)

Stack

Ferramenta Uso
Cloud Logging / Monitoring Nativo GCP — default na sua empresa
Vertex AI monitoring Métricas nativas do modelo
LangSmith Trace detalhado de LLM/agent calls
Braintrust Eval versionado, A/B de prompts

Como o time é GCP-first, comece por Cloud Monitoring e adicione LangSmith
se precisar de trace mais rico de agente.

Alertas mínimos

  • Error rate > 5% em 5 min
  • Latência p95 acima do SLA
  • Anomalia de custo (spike de tokens)
  • Eval score abaixo do threshold

Logging estruturado (com cuidado de segurança)

Logue: user_id (hash), timestamp, modelo, tokens in/out, latência, custo,
tools chamadas, eval score.

Nunca logue: conteúdo de prompt com PII, tokens de auth, dados de pagamento.
Ver Security-First Design.

Checklist

  • Tracing configurado em todas as calls
  • 4 alertas ativos e testados (dispare de propósito)
  • Dashboard com métricas em tempo real
  • Logging estruturado sem dados sensíveis
  • Consigo debugar um failure específico pelo trace
  • Runbook: o que fazer quando cada alerta dispara
