Enterprise Integrations — Slack, Atlassian, Zoom

Fase: 2 | Semanas: 11–12 | Projeto: P6 — Enterprise Integrations (Slack + Atlassian)

Perfil da função: "You've successfully rolled out and maintained integrations across a variety
of enterprise applications (Slack Enterprise Grid, Zoom, Atlassian suite)."

Este é o gap mais concreto entre a teoria e a prática. É também o mais rápido de fechar,
porque é engenharia de integração — algo que você já sabe fazer.

Slack (Enterprise Grid)

O que difere do Slack normal:
Enterprise Grid é multi-workspace, com org-level apps, políticas de admin, e
escopos por workspace. Um app que funciona num workspace pequeno pode falhar
em Grid por questões de instalação org-wide e permissões.

Conceitos essenciais:

Conceito Nota
Bot token vs User token Bot para automação; user token evite
Scopes Peça o mínimo — security review vai olhar isso
Events API vs Socket Mode Socket Mode para dev; Events API para prod
Slash commands Entrada natural para ferramentas internas
Modals / Block Kit UX rica sem sair do Slack
Rate limits Tier por método; planeje retry com backoff

Security-first (o perfil da função pede isso explicitamente):
- Verificar assinatura de request (X-Slack-Signature)
- Nunca logar token
- Secrets em Secret Manager, não em env var em plaintext
- Escopo mínimo necessário

📖 https://api.slack.com/docs
📖 Enterprise Grid: https://api.slack.com/enterprise/grid

Atlassian (Jira + Confluence)

Casos de uso da função:
- Jira: criar/atualizar tickets automaticamente a partir de conversas
- Confluence: fonte de documentos para RAG (documentation retrieval do perfil da função)

Conceitos:

Conceito Nota
REST API v3 Cloud; a v2 é legado
Auth OAuth 2.0 (3LO) para apps; API token para scripts
JQL Linguagem de query do Jira — vale aprender bem
Webhooks Para reagir a eventos em vez de fazer polling
Permissions Respeite as permissões do usuário, não do bot

⚠️ Ponto crítico de segurança: ao usar Confluence como fonte de RAG, os
resultados precisam respeitar as permissões de quem perguntou — não as do
service account. Isso é o access control do P6 — Enterprise Integrations (Slack + Atlassian).

📖 https://developer.atlassian.com/cloud/jira/platform/rest/v3/
📖 https://developer.atlassian.com/cloud/confluence/rest/v2/

Zoom

Menor prioridade que Slack e Atlassian, mas está no perfil da função.

Casos de uso: transcrições de reuniões como fonte de dados, automação de
agendamento.

⚠️ Transcrições contêm dados sensíveis. Trate como PII por padrão.

📖 https://developers.zoom.us/docs/api/

Padrão comum: tudo isso vira tool de agente

O ponto de conexão com Google ADK — Agent Development Kit: cada integração dessas vira uma tool
que o agente pode chamar. Construa as integrações primeiro (P6), depois
plugue no agente (P7).

Regra do PDF que se aplica aqui:

"Prompt injection via tools: tool returns malicious instructions that hijack
agent behavior. Sanitize tool outputs; treat tool results as untrusted data."

Uma mensagem do Slack ou um ticket do Jira é conteúdo não confiável.
Se um usuário escrever "ignore suas instruções anteriores" num ticket, seu
agente não pode obedecer.

Checklist

  • Slack app criado com scopes mínimos
  • Verificação de assinatura implementada
  • Slash command funcionando
  • Jira API: buscar e criar issues via JQL
  • Confluence API: buscar páginas
  • Permissões respeitadas (usuário, não service account)
  • Secrets em Secret Manager
  • Outputs das integrações tratados como untrusted (sanitização)
