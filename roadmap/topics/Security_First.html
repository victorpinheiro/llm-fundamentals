Security-First Design

Fase: 3 | Semanas: 20–21

Perfil da função: "You apply a security-first mindset, designing solutions that safeguard
data and systems while maintaining a seamless user experience."

Numa empresa de pagamentos, isso não é checkbox — é o que decide se sua
solução vai pra produção ou morre no review.

Superfícies de risco em sistemas de AI

Risco Exemplo no contexto sua empresa Mitigação
Prompt injection Ticket de Jira com instrução maliciosa Sanitizar; tratar como untrusted
Data leakage no prompt PII de merchant enviado ao modelo Redaction antes do call
Over-permissioned service account Bot vê docs que o usuário não pode ver Permissão do usuário, não do bot
Secrets em plaintext Token de Slack em env var Secret Manager
Logs com dado sensível Prompt logado com dados de cartão Redaction no logging
Model output não validado Output vira query SQL direto Structured output + validação

Access Control em RAG — o erro clássico

O bug mais comum e mais grave em RAG enterprise:
o retrieval usa as permissões do service account em vez das do usuário.

Resultado: alguém do Support pergunta algo e o bot responde com base num
documento de Legal que essa pessoa não deveria ver.

Padrões:
- Index-time filtering: namespaces separados por grupo de permissão
- Query-time filtering: filtro por metadata baseado no usuário
- Nunca confie só no prompt ("não responda sobre X") — isso é bypassável

Compliance relevante

Framework Por que importa aqui
GDPR Se sua empresa for europeia: data residency, right to deletion
PCI-DSS Pagamentos. Dados de cartão nunca vão pro prompt
SOC2 Audit trail, controle de acesso

Regra prática: se você não sabe se um dado pode ir pro modelo, assuma que não pode
e pergunte ao time de segurança/compliance antes.

Checklist de security review (faça no seu próprio sistema)

  • Secrets em Secret Manager, nunca em código ou env plaintext
  • Verificação de assinatura em todo webhook (Slack, Jira)
  • Permissões do usuário respeitadas no retrieval, não do service account
  • PII/dados de pagamento redactados antes do prompt
  • Logs sem dados sensíveis
  • Prompt injection testado (direto e via documento recuperado)
  • Output de LLM validado antes de alimentar qualquer sistema
  • Escopo mínimo em todas as integrações
  • Audit trail de quem perguntou o quê
