RAG — Architecture, Patterns & Failure Modes

Fase: 2 | Semanas: 9–10 | Projeto: P5 — RAG sobre Documentação (caso Legal)

O perfil da função pede "intelligent documentation retrieval" e "contract review automations".
Isso é RAG. É o coração técnico da função.

Decision Framework (PDF) — use antes de construir

1. Precisa de conhecimento que o modelo não tem?
   → Não: prompting sozinho basta.
   → Sim: continue.

2. A base cabe inteira no context window?
   → Sim: full-context stuffing (mais simples, sem erro de retrieval).
   → Não: RAG é necessário.

3. Acurácia e citação são obrigatórias?
   → Não: modelo base + prompting.
   → Sim: RAG com grounding instruction.

⚠️ No Vertex AI, considere antes: grounding nativo e Vertex AI Search podem
resolver o caso sem você construir pipeline próprio. Avalie primeiro —
é a escada de complexidade aplicada.

Chunking — a etapa mais mal compreendida (PDF)

"RAG systems do not universally require chunking. For short, atomic documents,
document-level retrieval is architecturally simpler and avoids fragmentation.
The first decision is whether to chunk at all — not which algorithm to use."

Estratégia Melhor para Cuidado
Sem chunking Docs curtos e atômicos (FAQs, políticas) Falha em docs longos
Fixed-size Corpus uniforme, impl rápida Corta no meio de frases
Sentence/paragraph Prosa geral Tamanhos variáveis
Semantic Docs heterogêneos, melhor qualidade Ingestão mais lenta
Parent-child Estrutura hierárquica (contratos!) Complexo de debugar

Para contratos (caso Legal do perfil da função), parent-child costuma fazer sentido:
cláusula como filho, contrato como pai.

Search Strategy — dado concreto do PDF

"Hybrid search is almost always better than either alone. Microsoft production
data shows hybrid (BM25 + vector) averages 48.4 relevance vs 43.8 for
vector-only and 40.6 for keyword-only."

  • Vector: acha por significado. Fraco em códigos, IDs, nomes exatos.
  • BM25: acha termo exato. Fraco em sinônimos.
  • Hybrid: merge via Reciprocal Rank Fusion (RRF).

Contexto sua empresa: números de contrato, IDs de merchant, códigos de erro —
tudo isso quebra vector search puro. Hybrid não é opcional aqui.

Failure Modes (PDF) — saiba de cor

Retrieval

Failure Exemplo Mitigação
Semantic mismatch "refund policy" vs "return procedures" Hybrid + query rewriting
Chunk fragmentation Resposta em 2 chunks, só 1 recuperado Parent-child, overlap
Top-k pequeno Relevante é o #6, você pega top-3 K maior + reranking
Stale index Doc atualizado, embedding não Re-index automático
Context poisoning Chunk irrelevante confunde geração Threshold de similaridade

Generation

Failure Mitigação
Hallucination apesar do contexto Grounding instruction explícita
Over-literalism (copia verbatim) Instrução de síntese
Context overflow Reranking + top-k menor

Advanced Patterns (PDF)

Padrão Quando usar
Query rewriting Queries vagas ou conversacionais
Reranking Quando precision no top-k importa
HyDE Queries curtas, documentos longos
Multi-query Perguntas complexas e multifacetadas

Vector DBs (PDF)

DB Melhor para Trade-off
pgvector Já usa Postgres (caso do perfil da função) Não escala >100M vectors
Vertex AI Vector Search Nativo GCP Lock-in, custo
Weaviate Hybrid nativo, OSS Curva de aprendizado
Qdrant Performance, self-hosted Ecossistema menor
Chroma Dev local Não é production-ready

O perfil da função cita Postgres explicitamente → pgvector é a aposta certa para começar.

Checklist

  • Decision framework aplicado e documentado
  • Avaliei grounding nativo do Vertex antes de construir do zero
  • Decidi SE chunkear (não assumi que sim)
  • Hybrid search com RRF implementado
  • Todos os failure modes testados
  • Pelo menos 1 advanced pattern implementado
  • Ragas: faithfulness > 0.85, answer relevancy > 0.80
