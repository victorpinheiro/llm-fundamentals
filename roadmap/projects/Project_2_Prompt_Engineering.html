P2 — Prompt Engineering + Structured Output

Semanas: 3–4 | Degrau: 1
Tópico: Prompt Engineering
Cobre do perfil da função: prompt engineering

Objetivo

Provar na prática a afirmação do PDF: 80% dos problemas de qualidade se resolvem
no prompt. Você vai medir isso, não acreditar.

O que construir

Evolução do classificador do P1, com 3 versões do mesmo prompt, medidas
nos mesmos 50 casos.

v1 — ingênuo:

Classifique este ticket em categoria e urgência.
Ticket: {ticket}

v2 — estrutura completa do PDF:

[ROLE] Você é um especialista em triagem de suporte interno...
[TASK] Classificar o ticket a seguir...
[CONSTRAINTS] Deve / não deve...
[FORMAT] JSON neste schema: {...}
[EXAMPLES] Boa: {...} Ruim: {...}
[FALLBACK] Se o ticket não estiver em inglês ou holandês, category = "needs_translation"

v3 — v2 + few-shot + chain-of-thought

Métricas a preencher

Métrica v1 v2 v3
JSON válido (%)
Categoria correta (%)
Urgência dentro de ±1
Latência média (ms)
Custo médio (USD)

Nota: v3 provavelmente tem qualidade maior e custo maior.
A conclusão certa pode ser "v2 vence" — chain-of-thought nem sempre paga.

Os 50 casos de teste

  • 20 happy path
  • 15 ambíguos (múltiplas categorias plausíveis)
  • 10 edge (outro idioma, vazio, muito longo, só emoji)
  • 5 adversarial (tentativa de prompt injection)

Entregável

p2_prompt_engineering/
├── prompts/
│   ├── v1_naive.txt
│   ├── v2_structured.txt
│   └── v3_cot.txt
├── router.py
├── test_cases.json         # 50 casos
├── evaluate.py
└── report.md               # tabela + conclusão

Definition of Done

  • 3 versões testadas nos mesmos 50 inputs
  • Tabela de métricas preenchida com números reais
  • Conclusão justificada: qual vai pra produção e por quê
  • Os 5 casos adversariais não quebraram o sistema
  • Zero regex
