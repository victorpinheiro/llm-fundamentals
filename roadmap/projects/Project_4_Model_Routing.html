P4 — Model Router

Semanas: 7–8 | Degrau: 1
Tópico: Model Selection & Cost/Latency Tradeoffs
Cobre do perfil da função: escolha de modelos, eficiência, "robust systems"

Objetivo

Reduzir custo em 50–70% sem degradar qualidade acima de 5%.
Padrão direto do PDF.

Numa automação interna que roda milhares de vezes por dia, isso é a diferença
entre um projeto aprovado e um projeto cortado por custo.

O que construir

Input → classificador de complexidade (modelo barato)
      → simple  → Gemini Flash-Lite
      → medium  → Gemini Flash
      → complex → Gemini Pro

Heurística de complexidade:
- Simple: classificação, extração, formatação
- Medium: sumarização, Q&A, geração curta
- Complex: raciocínio multi-passo, análise, código

Benchmark obrigatório

Rode os 50 casos do P2 em 3 configurações:

Config Custo total Qualidade Latência p95
Sempre Pro (baseline alto)
Sempre Flash-Lite (baseline baixo)
Router

Meta: router com ≥95% da qualidade do "sempre Pro", a uma fração do custo.

Se o router não bater essa meta, o resultado honesto é "roteamento não vale
a pena neste caso" — e isso também é um resultado válido para reportar.

Entregável

p4_model_routing/
├── router.py
├── complexity_classifier.py
├── benchmark.py
├── results/cost_analysis.md
└── tests/

Definition of Done

  • Router com 3 tiers funcionando
  • Benchmark completo nas 3 configurações
  • Economia real medida e documentada
  • Degradação de qualidade < 5% vs baseline alto
  • Projeção de custo mensal para 10k calls/dia
  • Prompt caching testado
